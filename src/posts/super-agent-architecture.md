## 当 Agent 能干活以后，人为什么还是很忙

设想一个研发场景：你让 Agent 排查接口超时，同时让另一个会话补测试，第三个会话处理代码评审。每个会话都能独立推进，但你仍然需要来回切换，解释背景、同步方案变化、检查有没有相互覆盖。

工具承担了执行工作，人却成了任务之间的信息中转站。

读完 DeepSeek 的[《Super-agent 设计探索：迈向更自主的 Agent 系统》](https://zhuanlan.zhihu.com/p/2099987320443237060)，我更关注的问题是：当多个任务同时发生，系统能否接住协调工作，让人的注意力集中在决策与验收上？

这篇文章是我的阅读整理与工程延伸。下文介绍的核心架构来自原文；研发示例与落地建议是基于这些思路的分析，未经本文实测。原文讨论的是架构探索，不能直接当作 DeepSeek Harness 的完整产品功能清单。

## Super-agent 要解决什么问题

在原文的语境里，Super-agent 是一种能够跨会话保持连续性、并行推进任务、响应环境事件并长期运行的 Agent 系统形态。

可以用四个问题理解它：

| 能力 | 用户实际关心的问题 |
| --- | --- |
| 连续 | 在群聊里说过的决定，到了 PR 评论里还认不认得？ |
| 高效 | 后台正在运行测试，前台还能不能接收新的要求？ |
| 主动 | CI 失败以后，是否还需要人再复制一次日志、重新发指令？ |
| 持久 | 进程重启或设备离线以后，任务能否保留并继续推进？ |

这套定义把关注点从一次对话的回答质量，扩展到了任务的整个生命周期。即使模型足够聪明，任务归属、消息投递、状态恢复等问题，也仍然需要系统设计。

## 用 Router 管协调，用 Worker 做执行

原文最核心的设计，是把全局协调和具体执行拆成两个逻辑层。

**Router 接住入口消息，识别任务归属，维护跨任务的关键决定，并统一对外回复。Worker 在隔离的上下文中执行具体任务，再向 Router 汇报结果。**

```text
群聊消息 / PR 评论 / CI 事件
            │
       过滤与订阅路由
            │
     新任务 → Router ← 关键结果
               │          ↑
          分派具体任务      │
               ↓          │
       Worker A   Worker B   Worker C
       排查超时    补充测试    处理评审
```

上图是便于理解的简化示意。已经确定归属的后续事件，可以直接投递给订阅它的 Worker。

这里有一个很实用的约束：Router 尽量不亲自执行耗时工作。否则它一边处理全局消息，一边进入复杂调试，很容易重新成为所有任务的阻塞点。

Worker 内部仍然可以拆分子任务，甚至组织自己的 Agent Team。区别在于职责：上层解决多个任务如何并行存在，下层解决一个任务如何完成。

对用户来说，最直观的变化是少了一项工作：不必先判断“这件事该去哪个会话里说”。系统负责把消息接回正确的任务。

## 事件驱动，需要先识别哪些事值得处理

接上群聊或代码平台之后，输入会从少量明确指令，变成大量持续到来的消息。闲聊、机器人通知、重复回调和真正的工作请求混在一起，全部交给模型判断会产生额外成本。

原文采用两级过滤：先通过程序判断来源、范围和白名单等明确条件，再让模型理解需要语义判断的候选事件。

在此基础上，引入三个对象会更容易理解后续流程：

- **Trigger**：一条具体事件，例如一次 CI 失败通知。
- **Thread**：一组有连续关系的事件，例如同一个 PR 下的讨论。
- **Worker**：负责推进任务的执行会话。

新任务由 Router 分派。Worker 订阅相关 Thread 后，后续评论和 CI 结果可以通过程序直达 Worker，减少重复的模型路由判断。一个任务也可以关联多个 Thread，例如同时关注群聊里的需求讨论与 GitHub 上的 PR。

我的工程理解是：**让模型处理不确定的任务归属，把已经确定的归属保存成可复用的系统状态。**

不过，收到同一条通知，只能让多个 Worker 有机会发现冲突，不能保证共享文件或共享环境的写入安全。实际实现仍需要目录隔离、资源锁或版本检查等机制。这是落地时应补上的约束。

## 上下文要能找回来，也要能更新

持续运行不意味着把所有历史永久塞进同一个提示词。长期积累的聊天、日志、评审记录，会很快挤占模型真正需要处理的信息。

原文用 Inline 与 Spill 描述两类操作：近期很可能用到的信息直接放入当前上下文；长内容和低频信息留在外部，当前只保留摘要、标识和续读入口。

对象之间再保留引用关系，就能沿着“当前消息 → 所属讨论 → 执行任务 → 关联评审”逐步找回背景。原文称之为链式召回。

我认为这里还有一个值得单独处理的问题：**找回旧决定以后，如何知道它是否仍然有效？**

例如用户先要求使用方案 A，后来在 PR 中改为方案 B。如果系统只召回“A 曾被采用”，没有召回后续变更，就会沿错误方向继续执行。

一个可考虑的做法，是为关键决定记录来源、版本和替代关系：

```text
任务：修复接口超时
当前决定：采用方案 B
来源：PR 中的确认评论
替代决定：方案 A
任务版本：v2
```

这是本文的实现建议。它把“记住对话”进一步落实为“知道当前应该依据哪个决定工作”。跨信道出现互相矛盾的指令时，还需要结合发起者权限和任务状态判断，不能只按消息到达顺序覆盖。

## 后台继续执行，前台也能改变方向

测试、构建和部署往往耗时较长。如果会话必须等工具执行结束，用户中途补充一句“先停一下”也无法及时生效。

原文提出异步工具交互：启动后立即返回任务标识，完成结果再以新事件送回会话，同时提供停止操作。这样，新指令不必等待后台工具全部结束；它仍然需要在系统能够处理输入的执行边界被接收。

从后端实现看，异步启动之后，还要回答几个具体问题：

- 用户已经叫停，稍后到达的成功回调还算不算有效？
- 需求已经变更，旧任务产物是否可以继续交付？
- 服务重启后，如何区分任务仍在运行、已经结束或状态未知？

我的建议是给任务设置明确状态，并让结果携带任务版本。处理结果时检查版本和当前状态，防止过期任务覆盖新的决定。停止也应区分“已请求停止”和“确认停止”，因为外部命令未必能瞬间终止。

这些细节决定了用户能否真正介入后台工作。

## 长期在线，需要拆开计算、状态和执行环境

原文把长期运行拆成两层解耦：先将推进 Agent Loop 的计算与持久状态分开，再将 Agent Loop 与实际执行环境分开。

| 部分 | 负责什么 |
| --- | --- |
| 计算 | 推进模型调用、处理事件、作出下一步决定 |
| 持久状态 | 保存任务、会话记录、订阅关系和恢复信息 |
| 执行环境 | 提供仓库、文件、依赖服务和具体工具链 |

这种划分允许计算进程重启后重新加载状态，也允许系统通过端侧 daemon 接入保留在原地的开发环境。

需要注意：云端协调服务在线，并不意味着离线电脑上的命令还能执行。设备不可达时，相关任务仍然需要等待、超时处理或重新选择环境。

下面这些可靠性机制，是我基于该架构的进一步建议：事件先持久化再确认接收，重复事件按唯一标识去重，运行中的任务通过租约或心跳声明执行权。对于创建 PR、发消息等外部写操作，还要记录操作结果，避免恢复时重复执行。

仅仅保存聊天记录，并不足以恢复一个已经对外产生影响的任务。

## Watchdog 应该检查任务有没有进展

Agent 可能一直在运行，却重复读同一段日志、反复尝试同一条失败命令。进程存活探测能看到它没有退出，却看不到它已经停滞。

原文在主系统外设置独立的 Watchdog，用外部控制回路检查基础设施故障与任务进展。

在实际实现中，我会先用规则识别可量化的异常，例如同类失败连续出现、长时间没有新增产物或超出预算，再让模型辅助分析原因。恢复动作也需要限制：重试次数有上限，策略修改有记录，扩大权限或预算时需要经过授权。

Watchdog 本身也可能判断错误。它的价值取决于能否提供可追溯、受约束的恢复，而不是可以无限制地修改主系统。

## 用一个研发任务串起来

以下是帮助理解的假设流程，并非我的实际部署记录。

团队在允许 Agent 观察的群聊里反馈：“某个接口在大数据量下超时。”系统按预设规则判断值得尝试，Router 创建排查任务，Worker 开始复现并记录证据。

复现成功后，Worker 准备修复并关联 PR。之后的 CI 结果和评审评论，通过订阅直接进入这个任务。用户在 PR 中改变方案时，系统更新当前决定；旧版本的执行结果仍可保留，但不能自动覆盖新方案。

如果执行设备掉线，任务进入等待状态。设备恢复后，系统核对工作目录、已有产物和未完成操作，再决定从哪里继续。若多次失败仍没有进展，Watchdog 汇总证据并请求必要的人类介入。

这个过程中，群聊适合接收简短结论，PR 适合承载改动说明和验证记录。需要人决定时及时通知，没有可用进展时保持安静。

## 怎样判断这套架构是否值得采用

原文的初步实验支持双层调度和订阅直通在其测试条件下的价值，但有明确边界：使用合成消息流，编码工作由耗时工具替代，每种方案运行五次。因此，它衡量的主要是调度与协作，不能直接证明真实代码质量或生产环境稳定性提升。

原文也指出，多会话方案会带来更多 token 消耗。评价时需要同时看任务耗时、结果质量、运行成本和人工介入，而不能只看并发任务数量。

如果准备验证，我会从一个仓库、一个明确的事件源和少量任务开始：先跑通任务分派、结果回传、重复事件去重与人工叫停，再逐步接入更多信道。

尤其需要提前定义权限边界。群聊内容和外部评论可以作为分析材料，是否构成执行指令则需要单独判断；跨设备工具访问也应按任务限制范围。主动尝试复现、准备草稿，与发布、合并或操作生产环境，应有不同的授权规则。

对我来说，Super-agent 最值得继续研究的地方，是把原本依赖人手动维持的连续性，变成系统能管理、能恢复、能审计的任务过程。接下来真正需要验证的是：它是否让人少花时间搬运信息，同时仍然看得懂任务进展，并能在必要时接管。
