## 为什么能写代码的 Agent，还需要一套新架构？

假设你同时让三个 AI 会话工作：一个修导出超时，一个开发搜索功能，一个处理代码评审。它们各自都能推进，但你仍要记住每个窗口做到哪里，把新的决定复制过去，再把测试结果转给对应的会话。

单个 Agent 越能干，这种协调工作反而越突出。模型负责执行，人负责维护任务之间的联系。

DeepSeek 在[《Super-agent 设计探索：迈向更自主的 Agent 系统》](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)中讨论的，就是怎样把这部分工作交给系统：让 Agent 持续接收工作环境里的消息，同时推进多个任务，跨群聊和代码平台接住上下文，并在长期运行中恢复异常。

**Super-agent 是一种 Agent 系统的设计方案。** 我理解这套方案的关键，是把模型分工、消息流转、任务记录和执行环境放在一起看。下面先看整体结构，再沿着一个任务的处理过程逐步展开。

DeepSeek 讨论的是架构探索，内部实例、公开研究原型和完整设计设想处于不同阶段，阅读时需要区分。

## 一张图看清整套方案

DeepSeek 为 Super-agent 提出四个目标：

| 目标 | 用户能感受到的变化 |
| --- | --- |
| 连续 | 在群聊里发起任务，到代码评审里继续说，也能接上背景 |
| 高效 | 几个任务并行推进，耗时命令运行时仍能接收新要求 |
| 主动 | 根据允许的规则关注环境变化，提前准备可用结果 |
| 持久 | 保存任务状态，支持跨设备工作和异常恢复 |

为了同时做到这些，系统分成几块：入口过滤、全局协调、任务执行、上下文管理、异步工具、持久化状态和外部巡检。

![Super-agent 总体架构：工作平台事件经筛选与路由进入执行会话，协调层统一回复，持久化状态和独立巡检支撑长期运行](/images/super-agent-architecture/architecture.svg)

*总体结构简图。箭头表示主要信息流，省略了具体平台接口。*

也可以用一家饭馆来记住这些职责：迎宾筛消息，前台接单分派，后厨执行，账本保存记录，店长检查进展。不过，落到技术设计上，有些职责由模型承担，有些由普通程序完成，并不需要每个角色都配置一个独立 Agent。

下面沿着“一个任务怎样进入、执行并持续推进”来看。

## 1. 双层架构：把全局协调与具体执行分开

### 为什么既不能全塞进一个会话，也不能每条消息都新开会话？

把所有任务交给一个会话，好处是背景集中。但一个模型循环通常按步骤推进：思考、调用工具、看结果，再继续。它一旦深入某个任务，其他任务就容易排队；不同任务的大量细节混在一起，也会影响判断。

反过来，每条消息都新开会话，虽然容易并发，却失去了连续性。上一条消息刚确认方案，下一条消息就可能在毫不知情的新会话中重新讨论；多个会话各自回复，也容易让用户摸不清谁在负责。

这套方案的做法，是分成两个逻辑层。

**Router 层负责全局协调。** 它承接人类交互，判断消息属于哪个任务，分派新工作，汇总跨任务的关键决定，并统一回复用户。

**Worker 层负责具体执行。** 每个 Worker 在独立上下文中处理任务，使用读写文件、运行命令等工具，向 Router 汇报关键状态和结果。

这里的“上下文”就是模型当前看到的材料。把 Worker 的上下文分开，能让修 Bug 的会话专注报错和代码，让开发功能的会话专注需求，减少相互干扰。

### Router 为什么尽量不干具体活？

如果协调员一边接消息，一边亲自运行耗时命令，它还是会变成阻塞点。所以 Router 只做交互和分派，甚至可以不给它 Bash 命令工具。

Router 的工作相对轻，DeepSeek 团队认为较轻量的模型往往就能兼顾速度和效果；Worker 直接影响任务结果与代码质量，通常需要更强的模型。

这也解释了它与常见 Agent Team 的侧重点差异：Agent Team 经常围绕一个复杂任务拆分角色；Super-agent 的 Router 首先协调多个任务。Worker 遇到复杂问题时，内部仍可组织子 Agent 或 Agent Team。

### 一个 Router 会不会忙不过来？

DeepSeek 团队没有一开始就把 Router 拆成多个会话，而是先采用一个常驻会话。当它正在处理上一轮消息时，新到的消息积累下来，下一轮合并处理。

例如，上一轮处理中收到三条新请求，下一轮可以一起判断归属、一起分派，而不用逐条做三次独立推理。这就是批处理。

它能降低平均开销，但也有上限：一次能放多少信息、模型能否准确处理多条请求，都有限制。Router 拆得越细，并发能力可能越高，但共享全局记忆也更难。按 DeepSeek 团队的实践，在文章所述的团队规模下，尚不必过早拆分。

## 2. 事件驱动：从“等你输入”变成“接住工作变化”

传统对话通常由用户输入一句提示词启动。持续在线的系统，则要接收群消息、代码评论、测试结果和日程提醒等变化。这类输入叫作 **Trigger，即事件**。

比如“导出失败了”是一条事件，某个代码修改请求（Pull Request，简称 PR）的测试失败通知也是一条事件。下文的 CI 指代码提交后自动运行的构建、测试等检查流程。

问题是，接上工作群以后，绝大多数消息都不需要它行动。全部交给模型判断，既花钱，也增加延迟。

### 第一步：先筛消息，再理解意思

过滤分为两级。

程序先检查明确条件，例如来自哪个群、哪个用户、是否属于允许接收的来源。有些消息直接忽略，有些只响应明确请求，有些作为候选信息继续处理。

剩下需要理解意思的消息，再交给模型，结合上下文和自然语言规则判断是否要行动。

这背后的原则很实用：**明确而稳定的判断交给程序，含义不确定的判断交给模型。** 省下的既是算力，也是后续任务的注意力。

### 第二步：新任务找 Router，旧任务直达 Worker

同一个 PR 下的评论和测试结果，或者同一个群聊话题下的连续讨论，构成一条 **Thread，可以理解为讨论串**。

Router 根据最初的消息创建 Worker 后，Worker 可以订阅相关讨论。之后，同一个讨论串里的消息由程序直接送到它那里，Router 无需每次再调用工具转发。

![事件处理流程：先做程序与语义筛选，再检查讨论串是否有订阅者；已订阅消息直达 Worker，新任务由 Router 分派](/images/super-agent-architecture/event-routing.svg)

*“直通”省去重复分派，Worker 的关键结果仍向 Router 汇报。*

一个 Worker 可以关注多个讨论串，比如同时关注群里的需求和 GitHub 上的 PR；一个讨论串也可以有多个 Worker 订阅。出现超出任务范围的新要求时，Worker 可以交回 Router 重新分派。

这解决了一个容易忽略的问题：**任务的边界与聊天地点的边界，并不总是一致。** 同一个任务会跨平台，一个群里也可能同时存在多个任务。

### 共享消息，不等于共享资源就安全了

DeepSeek 提到，多个 Worker 订阅同一讨论后，有机会从新事件中发现彼此的操作，进而处理冲突。但不能据此认为，同时修改同一文件就自动安全。

上下文隔离与文件隔离是两件事。是否使用独立目录、如何处理并发修改，仍是具体实现需要安排的工作。这是理解架构时应保留的边界。

## 3. 上下文管理：手边资料够用，历史资料找得到

任务持续运行，会积累大量消息、日志和代码。全部放进模型当前上下文，容量很快用完，重要信息也容易被淹没；只给一句摘要，又可能让模型反复查资料。

这套设计把上下文当作有限的工作台来管理，使用两个操作：

- **Inline**：近期很可能用到的内容，直接放进当前上下文。
- **Spill**：过长或低频使用的完整材料放在外部，当前只留摘要、编号和续读入口。

比如收到一条代码评论，直接附上评论内容、附近讨论和相关对象的编号；长日志只展示一部分，保留读取完整日志的入口。

### 怎样从一句“上次那个问题”找回背景？

系统为消息、讨论串和执行会话设置唯一编号，并保存它们之间的关联。查到一个对象时，也能看到下一步去哪里找。

![链式召回示意：从当前评论找到所属 PR，再找到负责的 Worker，最后找回关联群聊中的需求和决定](/images/super-agent-architecture/context-recall.svg)

*沿对象之间的引用逐步展开，避免每次加载全部历史。*

假设你在 PR 下说“还是按群里后来定的办法改”。系统可以从当前评论找到 PR，从 PR 找到负责的 Worker，再找到该任务关联的群聊讨论，读取后续决定。

这种做法叫作“链式召回”。它依靠可追踪的关联逐步补齐背景，缓解长期会话里信息丢失的问题。

但这并不意味着长期记忆已经解决。找得到记录、找对相关记录、判断哪个决定仍然有效，是不同难度的问题。DeepSeek 也明确指出，跨月甚至更久的记忆仍是扩展瓶颈。

## 4. 提前行动：用后台尝试，减少人的等待

筛选和路由解决“消息送给谁”，接下来还有“什么时候开始做”。

这里借用了投机执行的思路：即使还不确定结果会不会被采用，也可以在后台先做准备。有价值就交付，没有价值就丢弃，用额外算力换取更少等待。

DeepSeek 团队在内部研发中采用了一条策略：持续关注用户群中的问题反馈，先静默复现、寻找修复；确认问题并找到简单方案后，再交付结果，否则保持安静。

个人助手也能采用类似方式。收到会议邀请，先核对冲突、查相关背景、准备回复草稿，等用户确认。

这种设计的关键是“提前尝试”和“减少打扰”。主动程度要由规则控制：哪些来源可以触发，允许做哪些准备，何时需要人决定。算力消耗、误触发和外部操作风险，也会随主动程度提高而增加。

## 5. 异步交互：后台在跑命令，前台仍能接要求

如果 Agent 调用测试工具后一直等返回，用户中途说“先别测，需求改了”，也可能无法及时处理。

这套方案把耗时工具拆成启动与停止操作。启动后先返回“已开始”，完成结果随后作为新事件送回，模型循环不用一直等工具结束。

![同步与异步交互对比：同步方式等待工具完成，异步方式启动后可以处理新消息，再接收完成结果](/images/super-agent-architecture/async-interaction.svg)

*异步把对话响应与耗时执行分开。*

例如，Worker 启动一组测试，收到“已开始”后，仍能处理新消息。你补充“测试先停一下，改用另一套数据”，它可以据此调用停止操作，再调整工作。

这里有两个区别要讲清：一是不用等待后台工具完成，二是新输入仍在当前推理步结束后处理，并非任何时刻都能瞬间打断。原文写作时，这套异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。

### 结果该在哪里说、说多少？

多任务并行后，如果每个 Worker 都把推理和工具日志发到群里，人会被淹没。因此由 Router 统一对外交互，Worker 的执行细节保留在内部。

群聊适合简短结论、直接问题和需要决策的提醒。PR、邮件、文档适合完整说明背景、改动与验证。DeepSeek 团队采用了群聊单次回复不超过 100 词的约束，这是团队沟通实践中的一条规则，不是整个系统的通用性能指标。

## 6. 长期在线：把计算、记录和工作环境分开

本地 Agent 往往把三件事放在同一台电脑上：推进模型调用，保存会话，运行仓库里的工具。设备休眠或进程退出，就容易一起停下来。

这套方案分两步拆开这些绑定。

**先拆计算与状态。** 负责推进 Agent 的计算进程可以重启、替换，必须长期保存的会话等状态留在数据库。连续性依靠持久化记录，而不是依靠某个进程永远不退出。

**再拆计算与执行环境。** 模型调度放在云端，代码、文件、依赖和工具链可以留在原来的工作设备上。设备端运行轻量 daemon，也就是负责接收命令、执行并返回结果的常驻程序。

![计算、状态和执行环境分离：云端 Agent 读取持久化记录，通过端侧程序访问开发机或托管环境；离线设备需等待恢复](/images/super-agent-architecture/persistence.svg)

*这是一种部署设计，具体接入范围仍受权限与设备在线状态限制。*

为什么不直接把本地环境复制上云？因为真实工作环境可能包含未提交的修改、内网服务、特殊工具链和硬件依赖，完整同步成本很高。让环境留在原地，可以减少搬迁负担。

DeepSeek 也把这种方式与“脑手分离”联系起来：负责决策的部分与执行命令的环境可以独立安排，并按任务选择设备。

不过，云端在线并不会让离线电脑继续执行命令。某项工作依赖本地设备时，仍需等待设备恢复。保存了会话，也不意味着任何中断中的外部操作都能自动恢复正确；具体恢复能力要看实现。

## 7. Watchdog：检查系统活着，也检查任务在前进

一个进程没有退出，不能说明任务正常。Agent 可能反复运行失败命令，或者围着同一段日志打转。

因此，系统之外还需要一个独立的 Watchdog 会话，用定时消息驱动它检查两类事情：服务、接口、状态恢复等基础设施是否异常；Worker 是否有实质进展，方向是否偏离目标。

它是外部巡检与纠偏机制。主系统陷入问题时，不能完全依赖主系统自己判断自己是否正常。

方案中的 Watchdog 也具备工具能力，维护者可以询问原因，或者让它调整提示词和触发规则。这说明其设计目标包括在线维护，但也意味着巡检本身需要受控：它能改哪些东西、判断错误时如何处理，都是实现时要考虑的问题。

## 8. 实验说明了什么，又没有说明什么？

我觉得这组实验值得看，因为它比较的不只是“有没有子 Agent”，还比较了分工是否由系统结构保证、后续事件是否需要重复转发。

实验输入约 300 条消息，其中约 20 条是工作请求，其余包含闲聊、跟进、叫停与 CI 通知。真实编码用只消耗时间的工具代替，每种方案运行五次。因此它主要考察调度与协作。

| 对比 | 实验观察 | 我的理解 |
| --- | --- | --- |
| 完整 Super-agent | 任务完成时间 p50 为 12.4 分钟，p95 为 15.7 分钟 | 在该合成负载下，完成时间较短且稳定 |
| 单会话 + 子 Agent 工具，使用中性提示 | 五次都未调用子 Agent，p95 为 29.5 分钟 | 给了分工工具，模型也未必选择分工 |
| 单会话 + 子 Agent 工具，提示优先委派 | 五次中四次进行了委派，仍有一次自己执行形成长尾 | 提示能影响行为，但没有完全固定协调与执行的职责 |
| Super-agent 去掉直通 | 完成时间基本相同，Router 决定次数约增 30%，读缓存 token 约增 37% | 直通在该负载下主要降低开销，未表现出速度提升 |

p50 可以理解为一半任务能在这个时间内完成；p95 关注较慢的那部分任务。这里统计的是从工作请求到结果消息的时间，不能当作真实编码能力排行榜。

Router 的单独压力测试也支持了批处理的作用：需要决定的事件从每分钟约 1 条增加到约 40 条时，平均批量从 1.0 增至 2.8，单次请求耗时从 2.5 秒增至 3.9 秒，增长慢于批量大小。在该测试口径下，单个决定分摊的推理时间下降。

代价也很明确：多会话会带来更多 token 消耗。要判断方案是否合适，不能只看并发数量，还要看完成时间、实际结果、成本，以及省下多少人工协调。

## 9. 用一项修复任务串起这些设计

把前面的模块放回同一个假设场景，就更容易看懂它们的关系。

1. **发现消息。** 群里有人反馈导出超时。程序先检查来源，模型再按团队规则判断是否值得尝试。
2. **分配任务。** Router 创建排查工作，Worker 开始复现。Router 继续接收其他要求。
3. **关联讨论。** Worker 关注群里的话题与随后创建的 PR，评审评论、测试结果可以直接送达。
4. **补齐背景。** 用户在 PR 中改变方案，Worker 沿相关记录查到群里的决定与需求。
5. **持续交互。** 测试在后台运行，用户补充要求时，系统不用等整组测试结束才处理。
6. **交付结果。** 群里给简短结论，PR 中写清改动和验证。需要人决定时再提醒。
7. **应对中断。** 记录保存在持久化存储中；设备离线时等待恢复，巡检检查是否存在故障或停滞。

这些设计共同接走了任务组织、信息转发、背景查找和运行维护中的一部分工作。它们需要相互配合：只有多 Agent，没有消息归属与上下文关联，用户仍然要当中间人；只有持久化记录，没有恢复与巡检，也难以长期稳定推进。

## 10. 哪些问题还没有解决？

这套方案仍有适用范围。DeepSeek 列出了几个开放问题，也是我认为继续落地时值得关注的部分。

**规模更大时，如何继续分工？** 单个 Router 何时该拆分，Worker 之间何时需要直接交流，尚需更多场景检验。当前团队够用，不等于组织扩大后仍然够用。

**跨很久的记忆，如何保持可靠？** 引用关系能帮助找资料，但长期积累中的信息取舍、旧决定更新仍然困难。

**用户怎样掌握后台工作？** 隐藏底层会话以后，仍要提供合适的任务展示、介入和接管方式。省去窗口管理，不等于省去用户对关键步骤的控制。

**哪些信息可以放在一起？** 个人、团队、不同部门之间存在共享边界。多个独立 Super-agent 之间怎样协作，同时不暴露各自不该共享的上下文，也是开放问题。

**外部消息与设备凭据如何保护？** 系统持续接触群聊和评论，就会遇到不可信输入。如果云端 Agent 被攻破或受到提示词注入影响，其连接的设备也可能受到牵连。即使没有入侵，凭据进入模型上下文也可能泄露。DeepSeek 提出，需要研究让 Agent 使用凭据、却不直接接触凭据本身的机制。

因此，目前更适合把它理解成一套有内部实践支撑、仍在验证与完善的架构。官方公开的 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 明确标注为研究原型，并非 DeepSeek 正式产品，公开实现也不完全等同于文章与内部版本。

对这套方案最有价值的检验，是在真实工作里确认：它能否保持结果质量，让人少搬运信息、少维护会话，同时仍能看懂进度、改变方向并控制关键操作。
