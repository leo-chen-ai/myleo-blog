## 厨师很能干，老板为什么还这么累？

假设你开了一家饭馆，招来了几位手艺不错的厨师。

他们每个人都能做菜，但店里没有人接单、传话、记账。于是你忙得团团转：把客人的要求告诉厨师，记住哪桌改了菜，盯着哪道菜还没做好，再去回复等急了的客人。

用多个 AI 助手工作，有时就是这种感觉。

一个窗口修 Bug，一个窗口写功能，一个窗口看代码。它们各自能干活，但新的要求该告诉谁、哪个任务做到哪了、前面讨论过什么，还得你来记。

DeepSeek 的[《Super-agent 设计探索：迈向更自主的 Agent 系统》](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)，想解决的就是这个问题：**让 AI 承担更多任务协调，让人少花时间来回传话。**

读者提供的一张视频截图，把它比作一家“AI 饭馆”。这个比喻很适合入门。下面借用饭馆的思路，结合原文，从头讲清楚。

## 先看一家店是怎么运转的

一家能正常营业的饭馆，光有厨师还不够。

门口有人分辨哪些话需要理会，前台有人接单，后厨有人做菜，账本记住每桌的要求，店长还要检查有没有漏单、卡单。

Super-agent 也是这样组织工作的：

| 饭馆里 | AI 系统里做什么 |
| --- | --- |
| 迎宾 | 筛选消息，判断哪些值得处理 |
| 前台 | 接收要求，分配任务，统一回复 |
| 厨师 | 分头执行具体任务 |
| 传菜口 | 让后台干活和前台沟通衔接起来 |
| 账本 | 保存任务记录，需要时找回背景 |
| 店长 | 检查任务是否卡住，有没有实际进展 |

这些是帮助理解的角色，不是原文规定的六个独立程序。真正重要的是它们怎样配合。

## 前台接话，厨师专心做菜

你走进店里说：“来一份炒饭，再来一碗面。”

前台接下要求，把两份订单交给不同厨师。厨师各自忙自己的，前台仍然能招呼下一位客人。

原文的核心分工，就是这个意思。

**Router 可以理解成前台。** 它负责接消息、识别任务、安排执行者，最后统一回复你。

**Worker 可以理解成厨师。** 它拿到任务后，专心读代码、运行命令、检查结果。不同 Worker 可以同时处理不同事情。

![用饭馆理解 Super-agent：前台分单，后厨并行执行，账本保存记录，店长检查进展](/images/super-agent-architecture/restaurant.svg)

*根据原文与读者提供的饭馆比喻绘制。*

为什么不让前台顺便炒饭？因为它一旦进后厨忙上半小时，门口就没人接话了。所以原文强调，Router 不直接承担具体任务。

换成研发场景，就是一个 Worker 修导出超时，另一个 Worker 开发搜索功能。你只管提出要求，系统负责把事情交给合适的人。

这与常见的 Agent Team 侧重点稍有不同：Agent Team 经常是几个助手合作完成一件大事；这里首先解决的是，多件事如何同时推进。某件事特别复杂，负责它的 Worker 还可以再组织自己的小团队。

## 客人改了要求，消息要送到原来的订单

饭做到一半，你补了一句：“刚才那份炒饭不要放辣椒。”

前台得知道你改的是哪份订单，不能另开一份，也不能把要求告诉正在煮面的厨师。

AI 工作时也一样。你先在群里说“修一下导出超时”，后来到代码评审页面里说“别改数据库，换个办法”，系统需要知道，这两句话属于同一个任务。

原文把一组有关联的消息叫作 **Thread，可以理解为同一张订单下的讨论**。一条新评论、一次测试结果，则是一条新事件。

当 Worker 接手任务后，它可以持续关注相关讨论。后续评论和测试结果直接送给它，无需每次都由前台转述。这就是“订阅与直通”。

前台仍然掌握全局情况，执行者负责跟进细节。这样，换个地方说话也能接着办事，你不用重新解释一遍背景。

## 门口很热闹，但不用每句话都接单

有人进店点餐，有人在门口聊天，还有人只是路过。

如果听到一句话就让厨师开火，店很快就乱了。

接入工作群的 AI 也会收到大量消息。原文安排了两步筛选：先用程序检查消息来自哪里、是否在允许范围内，排除明显无关的内容；剩下需要理解意思的，再交给模型判断。

判断值得处理后，它还可以先做一点准备。

比如群里有人反馈：“导出一万条数据时总是失败。”团队如果事先配置了相应规则，Agent 就可以在后台尝试复现、寻找修复办法。有可用结果再拿出来，没有结果就保持安静。

个人助手也可以这样工作：收到会议邀请后，先查日程、准备回复草稿，等你确认。

**主动的价值，是让人少等、少催。** 能提前做哪些事，仍然要有明确范围。

## 菜还在锅里，你也能继续说话

一个常见的使用痛点是：AI 开始跑测试，你就只能等。想补充要求，也得等它忙完。

饭馆当然不能这样。厨房在做菜，前台仍然应该能接单、改要求。

原文的办法是把耗时操作放到后台：启动测试后，先返回“已开始”；测试结束，再把结果送回来。在此期间，系统可以处理新的消息，也可以根据要求发起停止操作。

这并不意味着能在任何瞬间立刻打断模型。原文说的是，新消息可以在当前推理步结束后被处理，不必等整个后台命令运行完。

回复也要分场合。在群聊里，像前台报菜一样给简短结论；在代码修改说明里，再写清问题、改了什么、怎样验证。厨师每次切菜、翻锅的细节，没有必要都拿到大厅广播。

## 账本记得住，也要翻得明白

饭馆不能只靠前台的脑子记住所有订单。但也没必要每做一道菜，就把开店以来的所有账本摊在灶台上。

AI 的上下文，也就是它当前能直接看到的材料，同样有容量限制。把所有聊天和日志都塞进去，重点反而容易被淹没。

原文采用的思路很直观：**当前要用的放在手边，其他资料留好摘要和查找入口。**

比如处理一条代码评论时，先提供评论内容、附近的讨论、对应任务的编号。需要知道最初为什么这么改，再顺着记录找到群里的需求。

这就是原文的“链式召回”：从眼前这条消息，逐步找回相关背景。

任务记录还要单独保存。负责调度的进程即使重启，记录仍在，系统才有依据接着处理。不过，这还不代表它拥有无限可靠的记忆；跨月甚至更长时间的记忆，原文也认为有待解决。

## 店长巡场，要看菜做出来没有

厨师一直站在灶台前，不等于菜一定在往前做。

Agent 也可能反复看同一段日志，反复运行失败的命令，看起来很忙，实际上没有进展。

原文在主系统之外安排了一个独立的 **Watchdog，可以理解成巡店的店长**。它定时检查服务有没有故障，也判断任务有没有推进、方向是否跑偏，发现异常后介入处理。

长期运行还需要把“调度工作”“保存记录”和“实际干活的机器”分开。比如调度在云端，代码与工具仍留在开发机上，通过一个轻量程序接收命令、返回结果。

这样不用把整套开发环境搬上云。但开发机离线时，系统无法继续在那台机器上执行命令，需要等它重新上线。

## 这家饭馆，已经开到什么程度了？

原文介绍，DeepSeek 团队的内部实例已经参与问题复现、修复和代码评审。但整篇文章讨论的是架构探索，公开的[研究原型](https://github.com/deepseek-ai/dsh-superagent-prototype)也明确说明，它并非正式产品，部分设计尚未实现。

作者还做了简化实验：给系统约 300 条消息，其中约 20 条是工作请求，真实编码用耗时工具替代，每种方案运行五次。

实验显示，明确分开协调与执行，比只提醒单个会话“适当找子助手”更稳定；后续消息直达执行者，主要节省了转发和判断的开销。但这验证的是调度，不能直接说明真实代码质量一定更好，多会话运行也会增加消耗。

还有几个现实问题：任务更多时如何协调，旧决定过很久还能否正确找回，不同人的资料怎样隔离，以及外部消息会不会诱导 Agent 做错事。尤其是能连接多台电脑以后，工具权限和凭据保护更加重要。

回到开头：这套设计想让人从忙着传单、催菜，逐步转向说清要求、确认结果。评价它有没有用，可以问一个很具体的问题：**完成同样的工作，我是不是少传了几次话、少盯了几个窗口？**
