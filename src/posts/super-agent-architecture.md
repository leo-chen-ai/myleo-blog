## AI 已经能干活了，为什么人还是很忙？

用过编程 Agent 的人，可能熟悉这样的场景：一个窗口修 Bug，一个窗口写功能，还有一个窗口帮忙看代码。每个窗口都能做事，但你得记住谁在做什么，还要把新的决定分别告诉它们。

比如，你在群里讨论完方案，又得把结论复制到 Agent 的窗口；测试失败了，还得把报错贴过去，让它继续排查。

**AI 接走了部分工作，协调这些工作的事仍然压在人身上。**

DeepSeek 的[《Super-agent 设计探索：迈向更自主的 Agent 系统》](https://zhuanlan.zhihu.com/p/2099987320443237060)，讨论的就是怎么减少这部分负担。下面按原文思路，用一个修 Bug 的例子来解释。

先说清楚：这是架构探索，部分设计已有内部实践和公开原型，不能把整篇文章当成已经上线的产品功能介绍。

## 先用一个例子理解它想做什么

假设团队群里有人说：“导出数据一多，页面就超时。”

按照原文设想的工作方式，在团队事先允许的范围内，Super-agent 可以先在后台尝试复现。确认问题并找到修复办法后，再提交一个 Pull Request（代码修改请求，下面简称 PR），请人检查。

你到 PR 里补充：“先别改数据库，换一种处理方式。”它能接上群里的背景，继续调整。测试结果出来后，它也能收到通知，接着处理，无需你再搬一次日志。

与此同时，另一个任务还可以照常推进。

原文把这种工作方式概括成四个特点：

| 特点 | 换成日常的话 |
| --- | --- |
| 连续 | 换个地方说话，也能接上同一件事 |
| 高效 | 几件事同时做，后台忙时还能接收新要求 |
| 主动 | 按预设规则发现值得处理的事，先做一些准备 |
| 持久 | 保存任务进度，支持长期运行和异常恢复 |

这里的 Super-agent，指的是一整套 Agent 系统的组织方式。理解它，先看系统怎么分工。

## 一个负责接话，多个负责干活

原文最核心的设计叫 **Router / Worker 双层架构**。名字看起来技术化，其实就是把“协调”和“执行”分开。

**Router 像接待兼协调员。** 它接收消息，判断是在说旧任务还是新任务，把工作交给合适的执行者，再统一回复用户。

**Worker 像具体办事的同事。** 一个排查导出超时，一个开发新功能，各自在自己的上下文里工作，减少无关信息的干扰。工作有进展，再汇报给 Router。

*根据原文双层架构思路绘制的简化图。*

为什么协调员不顺便自己修 Bug？因为它一旦钻进耗时的调试，就容易顾不上接收其他人的消息。所以原文强调，Router 尽量只做协调，把具体工作交出去。

对用户来说，这样做的好处很直接：**说清楚事情就行，系统来记住该找谁接着做。**

## 后续消息，自动送回正在做事的人

还是导出超时这个任务。开始时，Router 分配一个 Worker 排查；之后同一个 PR 下的评论、测试结果，都可以直接送给这个 Worker。

这就是原文说的“订阅与直通”。可以把它理解成：负责这件事的人关注了相关讨论，讨论一更新，它就能收到消息，无需协调员每次手动转发。

原文用了两个词来描述消息：

- **Trigger（事件）**：一条新消息，比如“这次测试失败了”。
- **Thread（讨论串）**：围绕同一件事的一组消息，比如一个 PR 下的连续讨论。

一个任务也可以同时关注群聊和 PR，让两边的信息接起来。

但群里的每句话都交给 AI 判断，既费钱也容易打扰人。因此原文先用程序筛掉明显无关的消息，再让模型判断剩下的内容是否值得处理。

“主动”的一个具体做法，是先在后台尝试：能复现、能找到有价值的修复，再把结果拿出来；没有可用结果时保持安静。能提前做哪些事，要由团队的规则限定。

## 记住事情，不等于把所有聊天都塞进去

长期工作的 Agent 会遇到越来越多的聊天、代码和日志。全部塞进当前上下文，模型反而容易抓不住重点。

原文的办法可以理解为：**手边放当前要用的资料，其余资料留好索引，需要时再翻。**

比如处理一条 PR 评论时，先给它这条评论、附近的讨论和相关任务编号。需要更多背景，再顺着关联找到群里的原始需求、之前的执行记录。

原文称之为 Inline & Spill，以及“链式召回”。不用死记名字，记住它解决的问题就够了：当前信息要够用，历史背景也要找得回来。

这种方式并没有解决所有记忆问题。原文也承认，跨月甚至更长时间的长期记忆，仍然是待解决的难点。

## 后台跑测试，前台还能说“先停一下”

如果 Agent 启动测试后必须一直等到结束，你中途补一句新要求，也只能排队。

原文把耗时操作改成异步：先启动任务，马上返回“已开始”；后台完成后，再把结果作为一条新消息送回来。

这样，测试运行期间，Agent 仍有机会处理你补充的要求，也可以发起停止操作。这里并非任何时刻都能瞬间打断模型，而是新消息不必等整个后台工具跑完，能在当前推理步结束后被处理。

回复方式也要适合工作场合：群聊里给简短结论，需要人决定时再提醒；PR 里则写清问题、改动和验证结果。用户需要看懂结果，没必要围观每一次工具调用。

## 想长期工作，还得保存进度、检查有没有卡住

原文接着讨论了两个容易被忽略的问题。

**第一，进程重启以后，任务还在不在？**

它把负责思考和调度的计算、保存任务的数据库、真正执行命令的机器分开。计算进程可以重启，任务记录仍然保留；代码和工具链也可以留在原来的开发机，通过一个轻量程序接收命令、返回结果。

当然，开发机离线时，它无法继续在那台机器上执行命令。原文的思路是支持设备重新上线后，再触发相关工作。

**第二，Agent 看起来在忙，是不是一直没进展？**

为此，原文安排了独立的 Watchdog，可以理解成巡检员。它既检查服务故障，也检查 Worker 是否反复失败、偏离目标，发现异常后介入处理。

保存进度负责“事情别丢”，巡检负责“别一直卡着”。这两件事，也是长期运行与一次性对话的重要区别。

## 现在做到哪一步了？

原文介绍，DeepSeek 团队的内部实例已经参与问题复现与修复、评审响应等日常工作。同时，作者也明确列出了尚未解决的问题，包括更大规模的协作、长期记忆、安全与隐私。

实验结果也要结合条件看：原文使用合成消息流，把真实编码替换成耗时工具，每种方案运行五次。它主要检验的是任务调度和协作，不能据此认定真实写代码一定更快、更好。多会话运行还会增加 token 消耗。

公开的 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 则明确标注为研究原型，并非 DeepSeek 正式产品；公开代码与内部版本、文章描述存在差异，部分设计尚未实现。

读完以后，我最关心的变化是：当 AI 能完成越来越多的具体工作，下一步需要减少的，是人来回搬运消息、维护任务背景和催促它继续干活的时间。

能不能做到这一点，比同时开了多少个 Agent 更值得关注。
